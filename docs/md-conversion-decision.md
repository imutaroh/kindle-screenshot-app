# 決定記録: Kindle のページ画像を Markdown にする方法

- 日付: 2026-10-12
- 状態: 採用（`internal/ocr` + `internal/markdown`、`kindlesnap capture` / `kindlesnap md` から使う）

## 結論

**Apple Vision の `RecognizeDocumentsRequest`（macOS 26、Swift 専用 API）を呼ぶ小さな Swift ヘルパーを使う。**
Go のバイナリにソースを `go:embed` で埋め込み、初回に `swiftc` でビルドして
`~/Library/Caches/kindlesnap/visionocr-<ソースの sha256 先頭12桁>` にキャッシュする。
Go からは外部コマンドとして複数ページをまとめて渡し、1ページ1行の JSON（段落・行・向き・座標・確信度）を受け取る。
Markdown への組み立て（柱・ルビの除去、見出し、ページをまたぐ段落の結合）は Go 側で行う。

## 背景と条件

- 対象は Kindle for Mac のウィンドウを撮った PNG。主に**縦書きの日本語**（右から左へ列を読む）
- リポジトリは pure Go（CGo なし・外部依存なし）を保ちたい
- 利用者の Mac に大きなランタイム（Python の venv・数 GB のモデル）を入れたくない
- 本1冊は数百ページあるので、1ページ数秒以内で、メモリも軽いことが望ましい

## 採用の理由

1. **精度と構造**: 縦書きの列を正しく右から左へ読み、段落の切れ目まで返す。c_inv では正解の9段落とぴったり一致した。
   生の出力の誤差（1.5%）は「柱（ページ上端の書名）」と「……」を「・・・・・」と返すことだけで、
   2つの決まった規則で取り除ける。行ごとの向き（縦・横）と座標、見出しの印も返すので、ルビや柱を幾何で判定できる
2. **軽さ**: モデルのダウンロードなし。ヘルパーは数百 KB、メモリは約135 MB、1ページ約1秒
3. **公開 API**: 同じ精度の LiveText（`ltmd`）は行の座標を非公開 API から取っていて、macOS の更新で壊れうる。
   `RecognizeDocumentsRequest` は公開 API
4. **ライセンス**: システムフレームワークだけなので、再配布や商用の制約がない。
   YomiToku（非商用のみ）や NDLOCR-Lite（DINOv3 の条件）のような確認事項がない
5. **pure Go を保てる**: Go からは外部コマンドとして呼ぶだけで、CGo も Python も要らない

## なぜ JXA / ObjC からは呼べないのか

pure Go から macOS のフレームワークを使う既存の手段は `osascript`（JXA）だが、どれも縦書きに届かなかった。

- **ObjC の `VNRecognizeTextRequest`**（ocrmac も JXA もこれ）: リビジョン3・ja-JP・accurate を指定しても、
  c_inv で返ったのは横書きの柱1行だけ（CER 99.3%）。縦書きを読むのは Swift 専用の新 API だけだった
- **`RecognizeDocumentsRequest` / Swift の `RecognizeTextRequest`** は Swift の構造体ベースの API で、
  ObjC ランタイムに出ていないので JXA からは呼べない
- **VisionKit（LiveText）を JXA から**: `ObjC.import('VisionKit')` は bridgesupport が無く失敗。
  クラスを動的に取っても、解析の完了コールバックが 10〜30 秒待っても呼ばれなかった
- **ショートカット（`shortcuts` CLI）**: ライブラリへの取り込みに GUI 操作が要り、出力も座標なしのテキストだけ

そのため「Swift のソースを同梱し、初回に `swiftc` でビルドする」形にした。代償として **Xcode Command Line Tools が必要**
（`xcode-select --install`）。ビルド済みバイナリを埋め込む案もあるが、ソースから作るほうが中身を確かめやすく、
アーキテクチャの違い（arm64 / x86_64）にも対応しやすい。

## 注意点・未確認のこと

- **すべて 1x（幅 1470px）の画像で測った。2x（Retina）は未測定。** 画素数が増えれば精度は上がると考えられるが、確かめていない
- **正解があるのは1ページ（の明暗2枚）だけ。** 柱・ルビ・見出しの規則はこのページと漫画数ページを見ながら作ったので、
  他の本のレイアウト（横書きの本、段組み、注釈の多い本）では外れる可能性がある。横書きの本は合成データでしか試していない
- **Claude がセッション内で読む方式の 0.0% は独立した証拠ではない。** 正解ファイル `truth_c.txt` はおそらく Claude が
  同じ画像を読んで作ったもので、Claude が書き起こし、Claude が検証している。人が打った正解での比較が必要
- **ダークモード**の画像はそのまま渡す。カラーマネージメントのかかった CIContext で白黒反転すると CER が 19% に悪化した
- **漫画**: 吹き出しの取りこぼし・誤読が多い（2ページ見開き・1x で特に）。漫画は PDF だけにする運用にした（`--no-md`）
- **表・図・手書き**: 表は表として認識されず、リストや段落として返る。図の中の文字は本文の後ろに引用（`> `）としてまとめる
- 確信度は弱い指標（正しく読めたページでも 0.25〜0.4）。要確認ページ（`review_pages`）は、ひどいページを拾う程度の目安
- ヘルパーのビルドは `swiftc` を直接呼ぶ。ベンチマークの検証では CommandLineTools の `swiftc` を絶対パスで呼ぶと
  標準ライブラリを読めず失敗し、`xcrun` 経由（`/usr/bin/swiftc` のシム）なら成功した。PATH 上の `swiftc` を使えば問題ない
- Intel Mac は未検証
